**기록 기준: 2026년 11월 20일. 프로젝트 표시는 복구했고, 기존 세션 7개의 UI 재연결은 미완료다.**

> **AI 활용 안내**  
> 이 글은 AI 에이전트(Codex)를 활용해 로컬 이전·조사 기록을 정리했습니다. 경로와 프로젝트 이름은 설명용 가상 예시이며 실제 계정·세션 식별자는 공개하지 않습니다. 이번 이슈가 발생한 Orca의 정확한 버전은 확인하지 못했습니다.

파일 복사와 서비스 검증이 끝나도 개발 도구의 작업 공간과 대화 연결까지 이전된 것은 아니었다. 이번에는 파일이 아니라 **앱이 경로를 기준으로 연결하던 작업 상태**가 문제였다.

## 파일과 서비스는 정상이었는데 프로젝트가 보이지 않았다

Mac의 저장 공간을 확보하려고 약 33GiB의 프로젝트를 외장 SSD로 옮겼다. 기존 경로에는 심볼릭 링크(다른 위치의 폴더를 기존 주소로 찾아가게 하는 연결)를 두어 도구들이 같은 주소를 계속 사용할 수 있게 했다. 다음 경로는 설명을 위한 예시다.

```text
~/Workspaces/music-lab
  → /Volumes/ExternalSSD/Workspaces/music-lab
```

사용 중인 에이전트와 터미널을 종료하고, 관련 컨테이너도 정지했다. 외장 SSD에 복사한 뒤 파일 내용을 대조하고, Git의 HEAD(현재 커밋)와 아직 커밋하지 않은 변경 상태도 확인했다. 경로를 전환하고 서비스를 다시 시작해 프로젝트 목록과 이미지·오디오 접근까지 확인했다.

여기까지는 정상으로 보였다. 하지만 이후 Orca에서 프로젝트가 보이지 않는 문제가 발견됐다.

## 같은 파일을 가리켜도 경로 문자열은 다를 수 있다

확인에 사용한 명령은 다음과 같다.

```sh
git -C ~/Workspaces/music-lab rev-parse --show-toplevel
```

기존 경로를 전달했지만 Git은 외장 SSD의 실제 경로를 반환했다. 심볼릭 링크가 기존 주소를 유지하더라도 모든 도구가 그 주소를 식별자로 사용하지는 않았다.

이 사례에는 네 가지 층이 있었다.

```text
파일: 외장 SSD에 실제 데이터가 존재
Git: 심볼릭 링크를 해석한 실제 저장소 경로 반환
Orca: 저장소 ID와 절대 경로를 조합한 워크스페이스 식별
세션: 기존 워크스페이스 ID에 연결된 대화 기록
```

파일 내용이 같다는 사실만으로 마지막 두 층까지 같아지는 것은 아니었다.

## 프로젝트 표시 복구와 대화 복구는 다른 작업이었다

기존 Orca 프로젝트에는 내부 경로가 등록되어 있었고 외부 워크스페이스 숨김 설정이 적용되어 있었다. 외장 실제 경로는 외부 워크스페이스로 인식되어 목록에 보이지 않았다.

해당 프로젝트의 외부 워크스페이스 표시를 허용한 뒤 외장 경로의 main 워크스페이스(주 작업 공간)가 다시 조회됐다. 저장소를 새로 등록하거나 파일을 다시 옮기지는 않았다.

그러나 대화 세션은 여전히 보이지 않았다. 추가로 세션 메타데이터(기록의 연결 정보를 담은 부가 정보)만 읽기 전용으로 조사한 결과 기존 세션 7개의 기록이 남아 있었고, 연결 대상이 모두 이전 내부 경로의 워크스페이스 ID였다.

```text
기존: <저장소 식별자>::<내부 프로젝트 절대 경로>
현재: <저장소 식별자>::<외장 프로젝트 절대 경로>
```

위 표기는 실제 식별자를 공개하지 않고 연결 구조만 단순화한 예시다. 저장소 ID가 같아도 뒤의 절대 경로가 달랐다. 프로젝트 표시 설정은 기존 세션의 연결 대상을 변경하지 않았다.

## 이번에 놓친 검증

처음에는 파일·Git·서비스 접근까지 확인한 뒤 이전이 끝났다고 판단했다. IDE(통합 개발 환경)에서 기존 프로젝트와 대화가 이어지는지까지는 확인하지 않았다. 프로젝트 표시를 복구한 후에도 세션 연결을 별도로 검증해야 한다는 사실을 늦게 확인했다.

등록된 42개 프로젝트의 경로와 Git 루트·표시 목록을 대조했을 때 다른 프로젝트에서 같은 경로 불일치는 발견하지 못했다. 기존 경로에 남은 세션 연결까지 추가로 조사했을 때 문제가 확인된 대상은 이 프로젝트의 7개 세션이었다.

이것은 해당 Mac에서 확인한 사례다. 모든 IDE나 모든 Orca 버전에서 같은 현상이 난다고 일반화할 수는 없다.

## 아직 해결되지 않은 부분

작성 시점인 2026년 11월 20일 기준으로 프로젝트 표시는 복구했지만 기존 세션의 UI 재연결은 완료하지 않았다. 기록이 존재한다는 것과 기존 화면에서 대화를 이어갈 수 있다는 것은 다르다.

세션 연결을 복구하기 위해 실행 중인 Orca 데이터베이스를 수정하거나 대화 기록을 삭제하지 않았다. 실행 중인 앱의 데이터베이스를 직접 수정하는 방법은 이 글에서 검증한 해결책이 아니다. 새 에이전트를 시작하는 명령도 기존 세션을 이전하는 기능으로 사용하지 않았다. 따라서 이 글은 완전한 세션 복구 성공기가 아니라, 저장소 이전에서 누락한 검증과 확인된 원인을 정리한 기록이다.

## 다음 이전에서 추가할 확인

- 파일 내용과 Git 상태를 대조한다.
- 새 저장 위치에서 서비스가 실제 파일을 읽는지 확인한다.
- Git이 반환하는 실제 루트 경로를 기록한다.
- IDE의 기존 워크스페이스가 그대로 표시되는지 확인한다.
- 기존 대화 탭과 세션이 연결되어 있는지 확인한다.
- 중요한 세션이 이어지는 것까지 확인한 후 내부 원본을 정리한다.

기존 주소에 연결 링크를 두는 것은 호환성을 돕는 방법이다. IDE의 경로 기반 식별자와 대화 연결까지 보존한다고 가정해서는 안 된다.

## 확인 근거와 기록의 범위

이 글은 2026년 11월 19일 프로젝트 이전 검증 기록, 11월 20일 Orca 표시 복구 기록, 후속 세션 메타데이터의 읽기 전용 조사 결과를 바탕으로 작성했다. 내부 저장 공간 관리 문서와 블로그 인계문을 대조했으며, 개인정보와 비공개 저장 경로를 포함하는 원본은 공개하지 않는다.

서비스 확인은 프로젝트 목록과 이미지·오디오 접근 등 기록된 범위에 한정된다. 전체 영상 재생이나 새 생성 작업까지 검증한 것은 아니다. 세션 기록이 남아 있다는 확인 역시 UI에서 대화를 이어갈 수 있다는 검증을 대신하지 않는다.

Orca의 공식 이전 절차나 모든 버전에 적용되는 복구 방법을 검증한 글은 아니다. 남은 작업은 **기존 세션 7개가 현재 워크스페이스에 연결되고, UI에서 다시 열리는지 확인하는 것**이다.
